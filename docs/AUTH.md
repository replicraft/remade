# Authentication with GitHub and Discord

Remade's directory stays static at `https://remade.wiki`. The Rust Worker in `apps/backend/remade-api/` serves login, callback, account lookup and logout at `https://api.remade.wiki/api/v1/auth/`. GitHub and Discord sign-in authenticate identity; UUIDv7 values generated by Remade identify users independently of their GitHub IDs. D1 is the shared Remade application database; its schema separates authentication from request engagement. Request upvotes and builder indications use the same sessions and shared database; see [Project Requests](PROJECT_REQUESTS.md). Accounts have no catalog publishing permissions or ownership claims.

The backend comes from Cloudflare's official workers-rs `templates/hello-world` template. It uses worker 0.8.7, worker-build 0.8.7, Rust 1.99.0 and root pnpm-managed Wrangler 4.149.0. Commit the backend Cargo.lock and root pnpm-lock.yaml. See [Cloudflare's Rust guide](https://developers.cloudflare.com/workers/languages/rust/) and [GitHub's OAuth flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps).

The header uses a provider-scoped Zustand store in `src/stores/auth-store.ts` for account lookup and logout, with login notification helpers in `src/lib/auth-notifications.ts`. The dropdown reads the store directly; session tokens are never stored in Zustand or browser storage. Separate auth islands synchronize confirmed account state through validated `remade-auth-changed` event payloads. Logout clears account settings immediately, and lookup generations prevent an older in-flight response from restoring stale account state.

The header uses Sonner to confirm successful sign-in with “Logged in as [provider username]” and successful sign-out with “Logged out”. A short-lived session-storage marker survives the OAuth redirect so returning page loads do not repeat the sign-in toast. A successful normal callback redirects home with a non-secret `auth_success` provider marker. Toasts and Last used updates require that marker, a recent matching pending attempt and a confirmed session containing that provider. Error redirects and ordinary account lookups cannot announce a new login; pending markers are consumed once. Unavailable browser storage does not block login.

Header login and account controls, request upvotes and builder indications are enabled in development and production. Local React and Worker integration tests remain available; production acceptance still requires a real OAuth login and logout against the deployed Worker.

## Provider choice and Discord setup

`/login/` is a static sign-in page. The header Login button opens a dropdown with provider logos; unauthenticated voting prompts open this page with the same provider options. After a confirmed session, the browser remembers the provider in local storage and labels it **Last used** on both surfaces. This preference contains only the provider name and makes no API request. GitHub and Discord are always shown, with no frontend feature flag. Configure both providers’ Worker credentials before deploying. Provider links work without JavaScript; JavaScript only records the pending sign-in notification. Opening the chooser makes no authentication API request for an anonymous visitor.

Discord follows the [authorization code flow](https://docs.discord.com/developers/topics/oauth2) with PKCE S256 and the `identify email` scopes. Verified email is used for duplicate-account checks; no guild membership or bot permissions are requested. GitHub requests `user:email` and reads `/user/emails`, including verified private and secondary addresses. The callback validates the exact `https://discord.com` issuer before exchanging the code, using Discord's [authorization-server metadata](https://discord.com/.well-known/oauth-authorization-server). Tokens are discarded after fetching `/api/v10/users/@me`; no refresh token is stored.

GitHub callbacks accept the exact `https://github.com/login/oauth` issuer documented in [GitHub's authentication discovery metadata](https://docs.github.com/en/apps/github-authentication-discovery-endpoints). Callbacks without an issuer remain supported for older GitHub responses; an unexpected or duplicate issuer is rejected before exchanging the code. Callback failures log only the provider and a fixed validation-stage label, without credentials or callback query strings.

Create a Discord application in the [Developer Portal](https://discord.com/developers/applications) and register these exact redirect URLs for the environments you use:

- Development: `http://localhost:8787/api/v1/auth/discord/callback`
- Production: `https://api.remade.wiki/api/v1/auth/discord/callback`

For development, fill `DISCORD_CLIENT_ID` and `DISCORD_CLIENT_SECRET` in the ignored `.dev.vars` using the existing example. For production, set the optional `DISCORD_CLIENT_ID` non-secret variable in Workers Builds before running `just backend::configure`; the generator adds it to `wrangler.generated.toml` when supplied. Store `DISCORD_CLIENT_SECRET` as a Worker runtime secret using the same generated config. Provisioning secrets and deployment remain explicit operator actions. Deploy the configured Worker before publishing the website changes.

### Operator setup checklist

1. Open the [Discord Developer Portal](https://discord.com/developers/applications), create an application named **Remade**, and open **OAuth2**. Copy its Client ID and generate/copy its Client Secret. This is website sign-in: no bot token, server installation or bot permissions are needed.
2. Under **OAuth2 → Redirects**, add the production callback above. Add the localhost callback as well if using that application for local testing. Save the changes. The website constructs the authorization URL and requests `identify email`; a generated bot invite is not needed.
3. In Cloudflare, open the **remade-api Worker → Settings → Build** and add `DISCORD_CLIENT_ID` to the build variables. The existing deploy script uses it to generate the runtime variable. Under **Settings → Variables and Secrets**, add `DISCORD_CLIENT_SECRET` with type **Secret**. Keep the existing GitHub and D1 settings. Do not put the client secret in Pages variables or any `PUBLIC_` variable.
4. Both providers appear automatically in the website build. Deploy the Discord-capable Worker with its credentials before publishing the updated website. No frontend feature variable or new D1 database is needed. Migration `0006_create_identity_emails.sql` is required for verified-email checks; the production deploy script applies pending migrations before deploying the updated Worker.
5. Before merging, test locally with both credentials in the Worker's ignored `.dev.vars` and the localhost origins from `.dev.vars.example`. In the frontend's ignored `.env`, set `PUBLIC_REMADE_API_BASE_URL=http://localhost:8787/api/v1`. Run `just backend::migrate-local`, then `just backend::dev`; start `pnpm dev` separately and visit `http://localhost:4321/login/`. Confirm Discord login, a request upvote, logout and the Last used label. Repeat with GitHub.

Cloudflare Pages preview hosts are not accepted OAuth origins by this Worker. Pointing a preview at the production API returns OAuth users to `https://remade.wiki`, not to the preview. Use localhost to test this unmerged implementation; final production acceptance happens after the operator deploys it. Runtime secret changes or production deployments remain operator actions.

Identities are keyed by `(provider, provider_user_id)`. Discord snowflakes remain strings. Usernames and email never automatically link accounts. A new identity whose verified email belongs to another account is redirected to `/login/` with guidance to use the existing provider and connect the other method. Missing or unverified addresses do not establish ownership and are not used for blocking. Email requests failing upstream abort sign-in rather than bypassing the check.

### Connecting sign-in methods

The account menu opens `/account/`. A signed-in user can POST an empty form to `/api/v1/auth/github/link` or `/api/v1/auth/discord/link`. These endpoints require the exact frontend Origin, a valid session and normal POST/body checks. The temporary signed OAuth cookie includes a distinct linking intent and the initiating session fingerprint. GitHub linking requests its account picker (`prompt=select_account`); Discord linking requests consent (`prompt=consent`). The callback requires that same live session, the provider's fresh authorization code, issuer validation, state and PKCE. A changed, expired or revoked session cannot complete linking; insertion checks session validity again inside the D1 transaction.

An unclaimed provider identity, or one already belonging to the current user, can be connected. If the freshly authenticated identity belongs to another account, explicit linking merges that account into the signed-in account only when a freshly verified provider email matches a fingerprint already observed on the signed-in account. Without that match, linking is rejected. Normal sign-in never merges accounts based on email alone.

Merging keeps the signed-in account's ID and profile, transfers all identities and unions request votes and builder indications. Overlapping activity counts once and retains its earliest timestamp. One atomic D1 batch rechecks the initiating live session, identity ownership and matching email observation, transfers activity and identities, revokes all sessions for both accounts and deletes the absorbed account. The callback issues a fresh session; other devices must sign in again. No new migration is required. New verified email observations for unclaimed identities must still belong to the current account or be unclaimed. After success the page confirms connection. Signing in through either connected provider resolves the same user ID, votes and builder indications. There is no unlink flow.

### Verified email data and migration

`0006_create_identity_emails.sql` adds private per-identity email fingerprints and a transaction-level ownership trigger. The existing users, identities, sessions and activity are preserved. Raw email addresses are not persisted or returned by `/me` or public exports. SHA-256 fingerprints of trimmed, ASCII case-normalized addresses are stored; these are still personal data, not anonymization. Dots and plus-address suffixes are not collapsed. Valid ASCII addresses are matched; unsupported formats are ignored. GitHub email reads are bounded to 100 addresses, with an overflow check rather than silently dropping addresses.

On each successful OAuth sign-in, verified observations are refreshed and addresses no longer reported for that identity are released. Existing users acquire observations on their next OAuth login, not through their current browser session. The system cannot retroactively detect private emails from before this change because provider tokens were discarded. Existing identities retain sign-in access even if a legacy account shares their email; that conflicting observation is not reserved. Historical duplicate accounts are not automatically merged or locked out. Different verified emails, aliases and missing addresses can still produce multiple accounts, so this is not a guarantee of one account per person.

Apply the migration locally with `just backend::migrate-local`. The approved production deploy script generates the production configuration, runs `pnpm exec wrangler d1 migrations apply DB --remote --config wrangler.generated.toml`, then deploys the Worker only if migrations succeed. Wrangler skips confirmation in CI and applies only pending migrations. The build script does not access production D1. Direct production commands remain operator actions.

## Local development

Install prerequisites once:

```sh
pnpm install --frozen-lockfile
rustup toolchain install 1.99.0 --component rustfmt --component clippy --target wasm32-unknown-unknown
cargo install worker-build --version 0.8.7 --locked
```

Create a separate development **GitHub OAuth App** with homepage `http://localhost:4321` and callback `http://localhost:8787/api/v1/auth/github/callback`. It is separate from the GitHub App used for catalog metadata. Copy `apps/backend/remade-api/.dev.vars.example` to `.dev.vars` in the same directory and fill in your development client ID and secret. The file is ignored; never commit its contents. The example overrides both origins to localhost.

```sh
just backend::migrate-local
just backend::dev
```

The Wrangler `[dev]` settings keep the request host at `localhost:8787` over HTTP. Without this explicit override, Wrangler can infer the production host from `routes`, causing the local authentication origin check to reject requests.

For local frontend configuration, set `PUBLIC_REMADE_API_BASE_URL=http://localhost:8787/api/v1` in `apps/frontend/remade-wiki/.env` and run `pnpm dev` in a second terminal. Alternatively, run `PUBLIC_REMADE_API_BASE_URL=http://localhost:8787/api/v1 pnpm dev` and visit **localhost**, rather than 127.0.0.1. An explicit API URL enables real sessions and request activity in development; without one, development uses signed-out accounts and preview activity. To test Discord locally, configure the Discord development credentials in `.dev.vars`. D1 state persists under `.wrangler/`. If your local database already applied the former combined `0001_init_auth.sql`, the split initial migrations require a fresh local database. Preserve any local data you need before resetting it; do not apply these rewritten initial migrations over an existing production schema. Only paired HTTP localhost origins enable development cookie names and omit Secure; production never uses this policy.

`just backend::check` checks Rust formatting and linting. `just backend::test` runs native Rust security tests only. Auth tests live in the frontend: `pnpm test:auth` builds the Wasm entrypoint and runs Vitest integration tests against actual workerd and local D1 with mocked GitHub and Discord responses. Unit, React and E2E auth coverage also stays in the frontend. `pnpm test` runs all four frontend suites; the auth integration suite requires the backend Rust toolchain and worker-build. CI runs frontend unit tests and native Rust checks; React, E2E and auth integration suites remain local.

## Security and behavior

- OAuth uses random 32-byte state and PKCE S256, separate provider callback URLs, and separate temporary cookies for GitHub and Discord. A signed, ten-minute HttpOnly cookie binds state, verifier and expiry to the initiating browser. Temporary cookies are cleared after callbacks, including failures. GitHub's single-use authorization code prevents successful replay. Redirects use configured fixed origins.
- Provider tokens exist only during the callback and are discarded after resolving the stable GitHub numeric ID or Discord snowflake. Verified email is read transiently and only private fingerprints are retained for duplicate checks; it never authorizes automatic account linking. Upstream responses are bounded to 64 KiB and ten seconds, and errors never expose credentials.
- D1 transactionally creates users and identities. The unique provider/ID constraint and email ownership trigger arbitrate concurrent first logins; a losing batch rolls back and reads the winner. Names can change without changing the Remade user ID. If an email claim appears after the first identity lookup, the callback checks for a concurrent winner of that same provider identity before treating it as a duplicate account.
- Session tokens contain 32 bytes from the Workers Web Crypto CSPRNG. D1 stores SHA-256 hashes only. Sessions expire after 30 days. Production cookies use `__Host-`, HttpOnly, Secure, SameSite=Lax, Path=/ and no Domain.
- `/me` returns 401 without D1 access for missing or malformed cookies. User-specific responses use `Cache-Control: no-store`. Logout requires the exact frontend Origin and rejects cross-site Fetch Metadata; CORS alone is not the CSRF defense.
- The non-secret `remade_login_hint` cookie is readable by the frontend across remade.wiki subdomains, but never grants access. Without it, anonymous page loads make **zero** auth API requests. With it, the small header island resolves the current account once on mount. The server-rendered header starts in a checking state and reserves an invisible fixed-size header slot until the browser determines session state. Without a hint it shows Login immediately after hydration; with a hint it waits for account lookup. Only a confirmed signed-out state shows Login, and lookup failures leave the controls hidden rather than flashing Login. An invalid session clears the hint. There is no polling or health check; API failure leaves the directory usable.
- Credentialed CORS allows only the configured frontend origin. Public catalog JSON retains its separate static export and wildcard CORS rules.

Production acceptance remains manual: test a real GitHub login and logout, and Discord login and logout, after DNS, Worker deployment, D1 migration and runtime credentials are configured. Check linking in both directions, verified-email collision guidance, cookies, `/me`, CORS, the mobile header and zero authentication API requests from a fresh anonymous browser (request counters use their own public totals endpoint). Local mocked-provider tests cannot prove production OAuth configuration works.

Request activity adds `0004_create_request_upvotes.sql` and `0005_create_request_builders.sql`, one table per migration. Apply locally with `just backend::migrate-local` before trying the development controls. Existing user tables are preserved. Production migrations run through the approved deploy script before Worker deployment; direct production commands remain operator actions.
