# Authentication with GitHub and Discord

Remade's directory stays static at `https://remade.wiki`. The Rust Worker in `apps/backend/remade-api/` serves login, callback, account lookup and logout at `https://api.remade.wiki/api/v1/auth/`. GitHub and optional Discord sign-in authenticate identity; UUIDv7 values generated by Remade identify users independently of their GitHub IDs. D1 is the shared Remade application database; its schema separates authentication from request engagement. Request upvotes and builder indications use the same sessions and shared database; see [Project Requests](PROJECT_REQUESTS.md). Accounts have no catalog publishing permissions or ownership claims.

The backend comes from Cloudflare's official workers-rs `templates/hello-world` template. It uses worker 0.8.7, worker-build 0.8.7, Rust 1.99.0 and root pnpm-managed Wrangler 4.149.0. Commit the backend Cargo.lock and root pnpm-lock.yaml. See [Cloudflare's Rust guide](https://developers.cloudflare.com/workers/languages/rust/) and [GitHub's OAuth flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps).

The header uses a provider-scoped Zustand store in `src/stores/auth-store.ts` for account lookup and logout, with login notification helpers in `src/lib/auth-notifications.ts`. The dropdown reads the store directly; session tokens are never stored in Zustand or browser storage.

The header uses Sonner to confirm successful sign-in with “Logged in as [provider username]” and successful sign-out with “Logged out”. A short-lived session-storage marker survives the OAuth redirect so returning page loads do not repeat the sign-in toast. Toasts appear only after the API confirms success; unavailable browser storage does not block login.

Header login and account controls, request upvotes and builder indications are enabled in development and production. Local React and Worker integration tests remain available; production acceptance still requires a real OAuth login and logout against the deployed Worker.

## Provider choice and Discord setup

`/login/` is a static sign-in page. Header Login links and unauthenticated voting prompts open this page. GitHub stays available; set frontend build variable `PUBLIC_REMADE_DISCORD_AUTH_ENABLED=true` to show **Continue with Discord** after configuring its Worker credentials. The default is disabled, so a GitHub-only deployment continues to work. The same setting works with `pnpm dev` locally. Provider links work without JavaScript; JavaScript only records the pending sign-in notification. Opening the chooser makes no authentication API request for an anonymous visitor.

Discord follows the [authorization code flow](https://docs.discord.com/developers/topics/oauth2) with PKCE S256 and the `identify` scope only. No email, guild membership or bot permissions are requested. The callback validates the exact `https://discord.com` issuer before exchanging the code, using Discord's [authorization-server metadata](https://discord.com/.well-known/oauth-authorization-server). Tokens are discarded after fetching `/api/v10/users/@me`; no refresh token is stored.

Create a Discord application in the [Developer Portal](https://discord.com/developers/applications) and register these exact redirect URLs for the environments you use:

- Development: `http://localhost:8787/api/v1/auth/discord/callback`
- Production: `https://api.remade.wiki/api/v1/auth/discord/callback`

For development, fill `DISCORD_CLIENT_ID` and `DISCORD_CLIENT_SECRET` in the ignored `.dev.vars` using the existing example. For production, set the optional `DISCORD_CLIENT_ID` non-secret variable in Workers Builds before running `just backend::configure`; the generator adds it to `wrangler.generated.toml` when supplied. Store `DISCORD_CLIENT_SECRET` as a Worker runtime secret using the same generated config. Provisioning secrets and deployment remain explicit operator actions. Enable the frontend build setting only after the Worker is configured and deployed.

Identities are keyed by `(provider, provider_user_id)`. Discord snowflakes remain strings; a GitHub and Discord ID with the same value cannot identify the same Remade account. Names and email never link accounts. There is no account-linking flow: using a second provider creates a separate account, with separate request activity. Existing GitHub users, sessions, votes and builder indications remain valid. The existing provider-independent D1 schema needs no new migration.

## Local development

Install prerequisites once:

```sh
pnpm install --frozen-lockfile
rustup toolchain install 1.99.0 --component rustfmt --component clippy --target wasm32-unknown-unknown
cargo install worker-build --version 0.8.7 --locked
```

Create a separate development **GitHub OAuth App** with homepage `http://localhost:4321` and callback `http://localhost:8787/api/v1/auth/github/callback`. It is separate from the GitHub App used for catalog metadata. Copy `apps/backend/remade-api/.dev.vars.example` to `.dev.vars` in the same directory and fill in your development client ID and secret. The file is ignored; never commit its contents. The example overrides both origins to localhost.

```sh
just backend::migrate-local
just backend::dev
```

The Wrangler `[dev]` settings keep the request host at `localhost:8787` over HTTP. Without this explicit override, Wrangler can infer the production host from `routes`, causing the local authentication origin check to reject requests.

For local frontend configuration, set `PUBLIC_REMADE_API_BASE_URL=http://localhost:8787/api/v1` in `apps/frontend/remade-wiki/.env` and run `pnpm dev` in a second terminal. Alternatively, run `PUBLIC_REMADE_API_BASE_URL=http://localhost:8787/api/v1 pnpm dev` and visit **localhost**, rather than 127.0.0.1. D1 state persists under `.wrangler/`. If your local database already applied the former combined `0001_init_auth.sql`, the split initial migrations require a fresh local database. Preserve any local data you need before resetting it; do not apply these rewritten initial migrations over an existing production schema. Only paired HTTP localhost origins enable development cookie names and omit Secure; production never uses this policy.

`just backend::check` checks Rust formatting and linting. `just backend::test` runs native Rust security tests only. Auth tests live in the frontend: `pnpm test:auth` builds the Wasm entrypoint and runs Vitest integration tests against actual workerd and local D1 with mocked GitHub and Discord responses. Unit, React and E2E auth coverage also stays in the frontend. `pnpm test` runs all four frontend suites; the auth integration suite requires the backend Rust toolchain and worker-build. CI runs frontend unit tests and native Rust checks; React, E2E and auth integration suites remain local.

## Production operator setup

No production resources or credentials are provisioned by the application or by CI. Complete these steps deliberately:

1. Register a GitHub **OAuth App**, with homepage `https://remade.wiki` and callback exactly `https://api.remade.wiki/api/v1/auth/github/callback`. No additional scopes or device flow are required. Configure `GITHUB_CLIENT_ID` as a Worker runtime variable and `GITHUB_CLIENT_SECRET` as a Worker runtime secret. These are unrelated to `REMADE_GH_APP_*` catalog credentials.
2. From `apps/backend/remade-api`, create D1 with `pnpm exec wrangler d1 create remade-db`. Export `GITHUB_CLIENT_ID`, `D1_DATABASE_NAME` and `D1_DATABASE_ID` (the returned UUID), or copy `apps/backend/remade-api/.env.example` to the ignored `.env` in that directory and fill them in. Run `just backend::configure` to generate ignored `wrangler.generated.toml`. The binding remains `DB`; `wrangler.toml` retains safe local defaults. Wrangler does not interpolate shell variables in TOML, so the generator writes validated deployment values explicitly. It does not deploy or create resources. Local development continues to read `GITHUB_CLIENT_ID` from `.dev.vars`.
3. Review the table migrations in order: `0001_create_users.sql`, `0002_create_user_identities.sql` `0003_create_user_sessions.sql`, `0004_create_request_upvotes.sql` and `0005_create_request_builders.sql` under `migrations/`. Each file keeps its table and indexes together. Then run `pnpm exec wrangler d1 migrations list DB --remote --config wrangler.generated.toml` and explicitly apply with `pnpm exec wrangler d1 migrations apply DB --remote --config wrangler.generated.toml`. Deployment does not apply migrations. Future schema changes get a new numbered file using `pnpm exec wrangler d1 migrations create DB <name> --config wrangler.generated.toml`; never edit an applied migration.
4. Store the runtime secret with `pnpm exec wrangler secret put GITHUB_CLIENT_SECRET --config wrangler.generated.toml` or the Worker's runtime settings. Configure `FRONTEND_ORIGIN=https://remade.wiki` and `API_ORIGIN=https://api.remade.wiki`. Do not put secrets in Workers Builds build variables or the frontend bundle.
5. Connect `remade-api` to this repository through **Cloudflare Workers Builds**, production branch `main`, root directory `apps/backend/remade-api`. Ensure the build image has rustup; if absent, provision it using the [official Rust installer](https://www.rust-lang.org/tools/install), then source its Cargo environment. Set the build command to `pnpm --dir ../../.. install --frozen-lockfile && rustup toolchain install 1.99.0 --profile minimal --target wasm32-unknown-unknown`. Set the non-secret Workers Builds environment variables `GITHUB_CLIENT_ID`, `D1_DATABASE_NAME` and `D1_DATABASE_ID`. Set the deploy command to `node --env-file-if-exists=.env configure-wrangler.mjs && pnpm exec wrangler deploy --config wrangler.generated.toml`. Wrangler's template build hook installs pinned worker-build and generates `build/index.js` and Wasm. Neither command applies remote migrations.
6. Attach the Worker custom domain `api.remade.wiki`, as declared in Wrangler config. Leave `remade.wiki` attached to the existing Pages project. The router also exposes `/api/v1/requests/activity` and empty POST actions for upvote/unvote/build/unbuild; it has no scheduled handlers or background jobs.
7. Worker build watch paths: include `apps/backend/remade-api/*`, `apps/frontend/remade-wiki/src/content/catalog/requests/*`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`; exclude nothing. Root tooling is included because Wrangler comes from the shared pnpm installation. Nested matches are covered by Cloudflare's wildcard.
8. Keep the existing Pages Git integration, root build and `apps/frontend/remade-wiki/dist` output. Verify Pages watch paths include `apps/frontend/*`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` and `cache/github-metadata.json`. Set frontend build variable `PUBLIC_REMADE_API_BASE_URL=https://api.remade.wiki/api/v1`, which is also the default. Only this public API base belongs in the frontend.

GitHub Actions validates the backend; it does not deploy, access production auth secrets or apply remote migrations. Its check always reports, but expensive validation runs only for backend, request-catalog or shared tool inputs, avoiding a pending required check on unrelated PRs.

## Security and behavior

- OAuth uses random 32-byte state and PKCE S256, separate provider callback URLs, and separate temporary cookies for GitHub and Discord. A signed, ten-minute HttpOnly cookie binds state, verifier and expiry to the initiating browser. Temporary cookies are cleared after callbacks, including failures. GitHub's single-use authorization code prevents successful replay. Redirects use configured fixed origins.
- Provider tokens exist only during the callback and are discarded after resolving the stable GitHub numeric ID or Discord snowflake. No email is collected or used to merge accounts. Upstream responses are bounded to 64 KiB and ten seconds, and errors never expose credentials.
- D1 transactionally creates users and identities. The unique provider/ID constraint arbitrates concurrent first logins; a losing batch rolls back and reads the winner. Names can change without changing the Remade user ID.
- Session tokens contain 32 bytes from the Workers Web Crypto CSPRNG. D1 stores SHA-256 hashes only. Sessions expire after 30 days. Production cookies use `__Host-`, HttpOnly, Secure, SameSite=Lax, Path=/ and no Domain.
- `/me` returns 401 without D1 access for missing or malformed cookies. User-specific responses use `Cache-Control: no-store`. Logout requires the exact frontend Origin and rejects cross-site Fetch Metadata; CORS alone is not the CSRF defense.
- The non-secret `remade_login_hint` cookie is readable by the frontend across remade.wiki subdomains, but never grants access. Without it, anonymous page loads make **zero** auth API requests. With it, the small header island resolves the current account once on mount. The server-rendered header starts in a checking state and reserves an invisible fixed-size header slot until the browser determines session state. Without a hint it shows Login immediately after hydration; with a hint it waits for account lookup. Only a confirmed signed-out state shows Login, and lookup failures leave the controls hidden rather than flashing Login. An invalid session clears the hint. There is no polling or health check; API failure leaves the directory usable.
- Credentialed CORS allows only the configured frontend origin. Public catalog JSON retains its separate static export and wildcard CORS rules.

Production acceptance remains manual: test a real GitHub login and logout, and Discord login and logout when enabled, after DNS, Worker deployment, D1 migration and runtime credentials are configured. Check cookies, `/me`, CORS, the mobile header and zero authentication API requests from a fresh anonymous browser (request counters use their own public totals endpoint). Local mocked-provider tests cannot prove production OAuth configuration works.

Request activity adds `0004_create_request_upvotes.sql` and `0005_create_request_builders.sql`, one table per migration. Apply locally with `just backend::migrate-local` before trying the development controls. Existing user tables are preserved. Remote migration and deployment remain manual operator steps; neither has been performed by this implementation.
